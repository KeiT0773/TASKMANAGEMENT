## 2. 共通方針

本書のすべての API に共通して適用する事項。

| No | 事項 | 決定 | 理由 |
| --- | --- | --- | --- |
| 1 | ベースパス | すべての API は `/api` で始まる（例：`/api/cards`） | 将来フロントエンドを同じサーバーから配信する場合に、画面の URL と API の URL を区別できる。既存の動作確認 API（`/api/health`）と同じ |
| 2 | データ形式 | 要求・応答ともに JSON（`Content-Type: application/json`） | React の `fetch` と Spring Web の標準的な組み合わせ |
| 3 | 項目名 | camelCase（例：`listId`、`dueDate`、`displayOrder`） | JavaScript / TypeScript の慣習に合わせる。DB の snake_case（`list_id`）との変換はバックエンドが行う |
| 4 | 日付 | `YYYY-MM-DD` の文字列（例：`"2026-09-22"`） | ISO 8601 の日付形式。`due_date`（`date` 型）に対応。時刻は持たない |
| 5 | 日時 | ISO 8601 の UTC 表記（末尾 `Z`。例：`"2026-09-20T01:00:00.123456Z"`） | `created_at` / `updated_at`（`timestamptz` 型）に対応。DB の保存値（UTC）をそのまま返し、日本時間への変換は画面に表示するときにフロントエンドが行う（データ設計書 5.4）。秒の小数部は DB の精度（マイクロ秒）まで含む |
| 6 | 値が無い項目 | JSON の `null` で返す。項目自体を省略しない | データ設計書 2. 方針 4（未入力は `NULL`）に対応。項目が常に存在する方がフロントエンドの型定義が単純になる |
| 7 | 区分値 | 優先度は `high` / `medium` / `low`、リストは `todo` / `doing` / `done` を DB の値のまま返す | 表示名（高 / 中 / 低、未着手 / 作業中 / 完了）への変換はフロントエンドが行う（データ設計書 9.）。画面モック `mock/script.js` と同じ値 |
| 8 | 識別子 | カードの `id` は数値、リストの `id` は文字列 | データ設計書 4.1・4.2 の型に対応 |
| 9 | 認証 | 行わない | 利用者 1 名・ローカル環境が前提（[要件定義書](requirements.md) 5.1）。サーバー配置時に再検討する |

### 2.1 エラー応答の形式

処理に失敗したときは、Spring Framework が標準で提供する **`ProblemDetail`**（[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) Problem Details for HTTP APIs）の形式で返す。

```json
{
  "title": "Not Found",
  "status": 404,
  "detail": "カードが見つかりません: id=999",
  "instance": "/api/cards/999"
}
```

| 項目 | 内容 |
| --- | --- |
| `type` | エラー種別を表す URI。本バージョンでは種別を細分化せず、既定値 `about:blank` のまま省略される（省略時は `about:blank` とみなす） |
| `title` | HTTP ステータスの標準的な名称 |
| `status` | HTTP ステータスコード（数値） |
| `detail` | 人が読むための説明。アプリが自分で投げる例外（404 など）は日本語。Spring が生成するもの（型不一致の 400 など）は英語のまま（例：`Failed to convert 'id' with value: 'abc'`） |
| `instance` | エラーが発生した要求のパス |

応答の `Content-Type` は `application/problem+json` になる。

独自のエラー形式を定義しないのは、標準の形式を使えば `@RestControllerAdvice` で例外を `ProblemDetail` に変換するだけで済み、応答の組み立てコードを自前で持たなくてよいためである（[技術スタック](tech-stack.md) 2. 構成を単純に保つ方針）。

#### 入力チェックのエラー（400）

登録・更新の要求 body が入力チェックに通らなかったときも同じ形式で返す。項目ごとの誤りは次のように含める。

```json
{
  "title": "Bad Request",
  "status": 400,
  "detail": "タイトルは必須です、優先度は high / medium / low のいずれかで指定してください",
  "instance": "/api/cards",
  "errors": [
    { "field": "title", "message": "タイトルは必須です" },
    { "field": "priority", "message": "優先度は high / medium / low のいずれかで指定してください" }
  ]
}
```

| 項目 | 内容 |
| --- | --- |
| `detail` | 項目ごとのメッセージ（日本語）を「、」でつないだもの。**フロントエンドはこれをそのまま表示すればよい** |
| `errors` | 項目ごとの内訳。`field` は要求 body の項目名、`message` はその項目のメッセージ。RFC 9457 が認める拡張メンバー（標準の 4 項目以外に追加してよい）として付ける |

`errors` を付けるのは、将来フロントエンドが項目のそばに個別のメッセージを出したくなったときに、`detail` の文字列を分解しなくて済むようにするためである。本版のフロントエンドは `detail` だけを使う。

要求 body が JSON として読めない場合（構文の誤り、`Content-Type` の不一致）は Spring が生成する 400 になり、`detail` は英語、`errors` は付かない。

### 2.2 使用する HTTP ステータス

| コード | 意味 | 本書での用途 |
| --- | --- | --- |
| 200 OK | 成功 | 取得・編集・移動に成功した。編集・移動では本文に更新後のカードを返す |
| 201 Created | 作成に成功 | 登録に成功した。本文に作成したリソースを、`Location` ヘッダーにそのリソースの URL（例：`/api/cards/7`）を返す |
| 204 No Content | 成功（本文なし） | 全リストの優先度順並べ替え（11.）または削除（12.）に成功した。返すべきリソースが無い（1 つに定まらない、または消えた）操作で使い、フロントエンドは `GET /api/cards` または `GET /api/cards?listId=` で取り直す |
| 400 Bad Request | 要求が不正 | パスやクエリの値が期待する型でない（例：`/api/cards/abc`）。要求 body が入力チェックに通らない（2.1）。body で指定した `listId` のリストが存在しない |
| 404 Not Found | 対象が存在しない | パスで指定した `id` のカードが無い（取得・編集・移動・削除とも） |
| 500 Internal Server Error | サーバー内部の失敗 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

## 4. リソースの形式

### 4.1 リスト

| 項目 | 型 | NULL | 内容 | 対応するカラム |
| --- | --- | --- | --- | --- |
| `id` | string | 不可 | `todo` / `doing` / `done` | `lists.id` |
| `name` | string | 不可 | 画面に表示する列の名称 | `lists.name` |
| `displayOrder` | number | 不可 | ボード上での並び順。左から 0, 1, 2 | `lists.display_order` |

```json
{ "id": "todo", "name": "未着手", "displayOrder": 0 }
```

> Java のクラス名は `List` だと `java.util.List` と紛らわしいため（データ設計書 12.）、`BoardList` とする。API のパス（`/api/lists`）と JSON の形には影響しない。

### 4.2 カード

| 項目 | 型 | NULL | 内容 | 対応するカラム |
| --- | --- | --- | --- | --- |
| `id` | number | 不可 | カードの識別子。DB が採番 | `cards.id` |
| `title` | string | 不可 | タスク名 | `cards.title` |
| `description` | string | 可 | 補足説明。未入力は `null` | `cards.description` |
| `dueDate` | string（日付） | 可 | 期限。未設定は `null` | `cards.due_date` |
| `priority` | string | 不可 | `high` / `medium` / `low` | `cards.priority` |
| `listId` | string | 不可 | 所属リスト。`todo` / `doing` / `done` | `cards.list_id` |
| `displayOrder` | number | 不可 | リスト内での表示順。0 始まり | `cards.display_order` |
| `createdAt` | string（日時） | 不可 | 作成日時 | `cards.created_at` |
| `updatedAt` | string（日時） | 不可 | 更新日時 | `cards.updated_at` |

```json
{
  "id": 1,
  "title": "資料作成",
  "description": "来週の定例会議で使う資料。\n前回の議事録を参照すること。",
  "dueDate": "2026-09-22",
  "priority": "high",
  "listId": "todo",
  "displayOrder": 0,
  "createdAt": "2026-09-20T01:00:00.123456Z",
  "updatedAt": "2026-09-20T01:00:00.123456Z"
}
```

期限超過かどうかはフロントエンドが判定する（データ設計書 5.4）ため、API は判定結果を返さない。

## 5. GET `/api/lists` — リスト一覧の取得

ボード画面（SC-01）の 3 つの列を描画するために、リストを並び順で返す。

### 要求

パラメータなし。

### 応答

| ステータス | 本文 |
| --- | --- |
| 200 | 4.1 の形式の配列。`displayOrder` の昇順 |

```json
[
  { "id": "todo",  "name": "未着手", "displayOrder": 0 },
  { "id": "doing", "name": "作業中", "displayOrder": 1 },
  { "id": "done",  "name": "完了",   "displayOrder": 2 }
]
```

リストは 3 件で固定（[要件定義書](requirements.md) 決定事項 No.1）のため、フロントエンドに定数として持たせる選択もある。それでも API を用意するのは、表示名を DB 側で一元管理し、フロントエンドが DB と食い違う値を持たないようにするためである。

## 6. GET `/api/cards` — カード一覧の取得

アプリを開いたときにボード画面（SC-01）が全カードを取得する（[データ要件書](data-requirements.md) 5. の D5「全カードの取得」）。

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| クエリ | `listId` | string | 任意 | 指定したリストのカードだけを返す。省略時は全件 |

```
GET /api/cards
GET /api/cards?listId=todo
```

### 応答

| ステータス | 本文 |
| --- | --- |
| 200 | 4.2 の形式の配列。`listId`、`displayOrder` の昇順（データ設計書 6.「取得時の並び」） |

```json
[
  { "id": 1, "title": "資料作成", "description": "来週の定例会議で使う資料。", "dueDate": "2026-09-22", "priority": "high",   "listId": "todo",  "displayOrder": 0, "createdAt": "2026-09-20T01:00:00.123456Z", "updatedAt": "2026-09-20T01:00:00.123456Z" },
  { "id": 2, "title": "買い物",   "description": "牛乳、卵、パン",           "dueDate": "2026-09-17", "priority": "medium", "listId": "todo",  "displayOrder": 1, "createdAt": "2026-09-20T01:00:00.123456Z", "updatedAt": "2026-09-20T01:00:00.123456Z" },
  { "id": 4, "title": "実装",     "description": null,                        "dueDate": null,         "priority": "medium", "listId": "doing", "displayOrder": 0, "createdAt": "2026-09-20T01:00:00.123456Z", "updatedAt": "2026-09-20T01:00:00.123456Z" }
]
```

- カードが 1 件も無い場合は空の配列 `[]` を返す（404 にはしない）。
- `listId` に存在しないリスト（例：`?listId=xxx`）を指定した場合も、エラーにせず空の配列を返す。絞り込み条件に合う行が無いだけであり、要求自体は正しいため。

### ボード全体を 1 回で返す API を用意しない理由

「リスト 3 件と、それぞれに属するカード」を入れ子の JSON で返す `/api/board` のような API も考えられるが、本版では採用しない。`/api/lists` と `/api/cards` の 2 回の要求で同じ情報が得られ、応答の形が平らな方が TypeScript の型定義と React の状態管理が単純になる。カードは最大 100 件程度（[要件定義書](requirements.md) 5.1）であり、2 回に分けても性能上の問題はない。

## 8. POST `/api/cards` — カードの登録

ボード画面（SC-01）の各リスト下部にある「＋ カードを追加」から、新しいカードを登録する（[機能要件書](functional-requirements.md) FR-01、[データ要件書](data-requirements.md) 5. の D1「カードの登録」）。

### 要求

`Content-Type: application/json` で、次の項目を持つ JSON を body に送る。

| 項目 | 型 | 必須 | 内容 | 入力チェック |
| --- | --- | --- | --- | --- |
| `title` | string | 必須 | タスク名 | 前後の空白を除いて 1 文字以上、100 文字以内（データ設計書 4.2 `title varchar(100)`、`ck_cards_title`） |
| `priority` | string | 任意 | `high` / `medium` / `low`。省略または `null` のときは `medium` | 3 つの値のいずれか |
| `listId` | string | 必須 | 追加操作を行ったリストの `id`（`todo` / `doing` / `done`） | `lists` テーブルに存在すること |

```
POST /api/cards
Content-Type: application/json

{ "title": "資料作成", "priority": "high", "listId": "todo" }
```

- `description`（説明文）と `dueDate`（期限）は **受け取らない**。FR-01 のとおり登録時点では未設定（`null`）とし、後から編集 API（FR-02、追記予定）で設定する。body に含まれていても無視する。
- `id`・`displayOrder`・`createdAt`・`updatedAt` はサーバーが決める。body で指定しても無視する。
- `title` の前後の空白はサーバーが取り除いてから保存する。空白だけの `title` は「必須」の違反として 400 になる。

### 処理

1. `listId` のリストが存在することを確認する（無ければ 400）。
2. `title` の前後の空白を除き、`priority` が無ければ `medium` を補い、カードを **そのリストの末尾** に追加する。
3. そのリストのカード全件を [機能要件書](functional-requirements.md) 3.1「優先度順の並べ替え規則」に従って並べ直す（高 → 中 → 低。同じ優先度の中では元の順序を維持する安定ソート）。末尾に追加してから並べ直すため、新しいカードは **同じ優先度のカードの末尾** に入る。
4. 並べ直した結果を `displayOrder` に 0 からの通し番号として書き込む（[データ設計書](data-design.md) 6.「振り直しを行う操作」）。`displayOrder` が変わった既存カードは `updatedAt` も現在時刻に更新する。
5. 2〜4 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

### 応答

| ステータス | 本文 |
| --- | --- |
| 201 | 4.2 の形式のオブジェクト 1 件（登録したカード）。`Location` ヘッダーに `/api/cards/{id}` |
| 400 | 入力チェックに通らない（2.1「入力チェックのエラー」の形式、`errors` 付き）。`listId` のリストが存在しない（`detail` は `リストが見つかりません: listId=xxx`、`errors` なし）。body が JSON として読めない（Spring 生成、英語） |
| 500 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

```
HTTP/1.1 201 Created
Location: /api/cards/7
Content-Type: application/json

{
  "id": 7,
  "title": "資料作成",
  "description": null,
  "dueDate": null,
  "priority": "high",
  "listId": "todo",
  "displayOrder": 1,
  "createdAt": "2026-09-21T01:00:00.123456Z",
  "updatedAt": "2026-09-21T01:00:00.123456Z"
}
```

### 登録後に画面へ反映する方法

応答で返るのは登録したカード 1 件だけだが、処理 3〜4 のとおり **同じリストの他のカードの `displayOrder` も変わりうる**。フロントエンドは応答の 1 件を手元の一覧に差し込むのではなく、成功後に `GET /api/cards?listId=<登録したリスト>`（6.）でそのリストを取り直して置き換える。これにより、並べ替えの規則をフロントエンドに持たせずに済み、フロントエンド設計書 5.「フロントエンドでは並べ替えを行わない」を維持できる。

### 並べ替え後の一覧を応答で返さない理由

「登録後のリスト全件を返す」形にすれば通信は 1 回で済むが、「作成したリソース 1 件を返す」という REST の一般的な形から外れ、他の API と応答の形が揃わなくなる。カードは最大 100 件程度（[要件定義書](requirements.md) 5.1）であり、リスト 1 つ分を取り直す負担は小さいため、応答の形の一貫性を優先する。

### `listId` が存在しないときに 404 ではなく 400 にする理由

404 は「要求したパスのリソースが無い」ことを表す。`POST /api/cards` というパス自体は存在しており、誤っているのは body の中の値であるため、「要求が不正」を表す 400 を使う。

## 9. PUT `/api/cards/{id}` — カードの編集

カード詳細（SC-02）で、タイトル（FR-02）・説明文（FR-06）・期限（FR-07）・優先度（FR-08）を編集する（[データ要件書](data-requirements.md) 5. の D2「編集」）。カード詳細には「保存」ボタンが無く、項目ごとに確定したとき（入力欄からフォーカスが外れたとき、または値を変えたとき）にフロントエンドがこの API を呼ぶ（フロントエンド設計書 8.6）。

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| パス | `id` | number | 必須 | 編集するカードの識別子 |

`Content-Type: application/json` で、次の **4 項目をすべて** body に送る。変更していない項目も現在の値を送る。

| 項目 | 型 | 必須 | 内容 | 入力チェック |
| --- | --- | --- | --- | --- |
| `title` | string | 必須 | タスク名 | 前後の空白を除いて 1 文字以上、100 文字以内 |
| `description` | string / null | 必須（`null` 可） | 補足説明。複数行可 | 2000 文字以内。空文字・空白のみは `null` として保存する（データ設計書 2. 方針 4） |
| `dueDate` | string（日付）/ null | 必須（`null` 可） | 期限。`null` で解除 | `YYYY-MM-DD` の形式。過去の日付も可 |
| `priority` | string | 必須 | `high` / `medium` / `low` | 3 つの値のいずれか |

```
PUT /api/cards/1
Content-Type: application/json

{ "title": "資料作成", "description": "来週の定例会議で使う資料。", "dueDate": "2026-09-22", "priority": "high" }
```

- `listId` と `displayOrder` は **含めない**。リスト間の移動と並べ替えは 10. の API で行う。body に含まれていても無視する。
- `id`・`createdAt`・`updatedAt` はサーバーが決める。body で指定しても無視する。
- `dueDate` が `YYYY-MM-DD` として読めない文字列（例：`"2026/09/22"`）のときは、body が JSON として読めない場合と同じく Spring が生成する 400（英語の `detail`、`errors` なし）になる。フロントエンドは日付の入力欄（`<input type="date">`）からこの形式でしか送らないため、日本語のメッセージは用意しない。

### 処理

1. `id` のカードを取得する（無ければ 404）。
2. `title` の前後の空白を除き、`description` が空文字・空白のみなら `null` にして、4 項目をカードに書き込み、`updatedAt` を現在時刻にする。
3. **`priority` が変更前と異なるときだけ**、そのカードをリストの末尾に移してから、8.「処理」3〜4 と同じ規則（[機能要件書](functional-requirements.md) 3.1）でリスト内を並べ直し、`displayOrder` を 0 からの通し番号として書き込む。これにより、変更したカードは **変更後の優先度グループの末尾** に入る（FR-08）。
4. `priority` が変わっていないときは、並びには触らない（タイトル・説明文・期限の編集で位置は動かない）。
5. 2〜3 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

### 応答

| ステータス | 本文 |
| --- | --- |
| 200 | 4.2 の形式のオブジェクト 1 件（編集後のカード） |
| 400 | 入力チェックに通らない（2.1「入力チェックのエラー」の形式、`errors` 付き）。`id` が数値でない。body が JSON として読めない、または `dueDate` が日付として読めない（Spring 生成、英語） |
| 404 | 指定した `id` のカードが存在しない |
| 500 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

```json
{
  "id": 1,
  "title": "資料作成",
  "description": "来週の定例会議で使う資料。",
  "dueDate": "2026-09-22",
  "priority": "high",
  "listId": "todo",
  "displayOrder": 1,
  "createdAt": "2026-09-20T01:00:00.123456Z",
  "updatedAt": "2026-09-21T02:00:00.123456Z"
}
```

### 編集後に画面へ反映する方法

優先度を変えたときは、8. と同じく同じリストの他のカードの `displayOrder` も変わりうる。フロントエンドは成功後に `GET /api/cards?listId=<そのカードのリスト>`（6.）でリストを取り直して置き換える。優先度以外の編集でも同じ手順にし、「編集したら取り直す」の 1 通りにそろえる（フロントエンド設計書 5.4）。

### 4 項目をまとめて送る（PUT）理由

項目ごとに保存するのだから、変えた項目だけを送る `PATCH` も考えられる。しかし `PATCH` では「`dueDate` を `null` にして解除したい」と「`dueDate` は送っていない（変更しない）」を区別する仕組みが要り、要求の形が複雑になる。フロントエンドはカード詳細に 4 項目の現在値を持っているため、毎回 4 項目を送るのは容易であり、要求の形を 1 つにできる `PUT`（編集できる項目の置き換え）を採る。

## 10. PUT `/api/cards/{id}/position` — カードの移動・並べ替え

ボード画面（SC-01）でカードをドラッグ&ドロップしたときに、別のリストへの移動（FR-04）と、同じリスト内の並べ替え（FR-05）を保存する（[データ要件書](data-requirements.md) 5. の D1「移動・並べ替え」）。どちらも「移動先のリストと、その中での位置」を指定する 1 つの API で扱う。

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| パス | `id` | number | 必須 | 動かすカードの識別子 |

| 項目 | 型 | 必須 | 内容 | 入力チェック |
| --- | --- | --- | --- | --- |
| `listId` | string | 必須 | 移動先のリストの `id`。同じリスト内の並べ替えでは現在のリストを指定する | `lists` テーブルに存在すること |
| `displayOrder` | number | 必須 | 移動先のリストで、**自分を除いた並び** の何番目（0 始まり）に入るか。リストの枚数以上なら末尾 | 0 以上の整数 |

```
PUT /api/cards/3/position
Content-Type: application/json

{ "listId": "doing", "displayOrder": 1 }
```

### 処理

1. `id` のカードを取得する（無ければ 404）。
2. `listId` のリストが存在することを確認する（無ければ 400）。
3. 移動元のリスト（カードの現在の `listId`）の並びからそのカードを外す。
4. 移動先のリストの並び（移動元と同じリストなら 3. で外したあとの並び）の `displayOrder` の位置にカードを差し込む。位置が枚数以上なら末尾に置く。別のリストへ動かしたときはカードの `listId` を書き換える。
5. 移動元と移動先のリストそれぞれについて、`displayOrder` を 0 からの通し番号として書き直す（同じリストなら 1 つ）。動かしたカードと、位置が変わったカードは `updatedAt` を現在時刻にする（[データ設計書](data-design.md) 6.「振り直しの単位」）。
6. **優先度順の並べ替えは行わない**。ドロップした位置がそのまま保存される（FR-04、FR-05、機能要件書 3.1「ドラッグによる並べ替えおよびリスト間の移動では、この規則による並べ替えは行わない」）。
7. 3〜5 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

### 応答

| ステータス | 本文 |
| --- | --- |
| 200 | 4.2 の形式のオブジェクト 1 件（移動後のカード。`listId` と `displayOrder` が新しい値） |
| 400 | 入力チェックに通らない（`displayOrder` が負、`listId` が空。2.1 の形式）。`listId` のリストが存在しない（`detail` は `リストが見つかりません: listId=xxx`）。`id` が数値でない、body が JSON として読めない |
| 404 | 指定した `id` のカードが存在しない |
| 500 | DB に接続できないなど。フロントエンドは元の位置に戻し、「保存されていない」旨を通知する（FR-09） |

```json
{
  "id": 3,
  "title": "読書",
  "description": null,
  "dueDate": null,
  "priority": "low",
  "listId": "doing",
  "displayOrder": 1,
  "createdAt": "2026-09-20T01:00:00.123456Z",
  "updatedAt": "2026-09-21T02:00:00.123456Z"
}
```

### 移動後に画面へ反映する方法

移動元・移動先の両方のリストで `displayOrder` が振り直されるため、フロントエンドは成功後に `GET /api/cards?listId=` を移動元と移動先について呼び（同じリストなら 1 回）、取り直して置き換える。ただしドラッグ&ドロップでは、ドロップした瞬間にカードがその位置に見えている必要があるため、フロントエンドは API を呼ぶ前に手元の並びを先に変える（楽観更新）。詳細はフロントエンド設計書 5.5。

### 編集 API（9.）に `listId` を含めない理由

編集（カード詳細）と移動（ドラッグ&ドロップ）は画面上の別の操作であり、移動だけが 2 つのリストの振り直しを伴う。1 つの API に混ぜると、「優先度も変わりリストも変わった」ときにどちらの規則を適用するかが複雑になる。分けておけば、9. は「優先度が変わったら並べ直す」、10. は「並べ直さない」と規則が 1 つずつで済む。

### 位置の指定を「自分を除いた並びの何番目か」とする理由

ドラッグ&ドロップのライブラリ（`@hello-pangea/dnd`）が返す移動先の `index` がこの定義であり、フロントエンドが値を変換せずにそのまま送れる。同じリスト内で下へ動かすときに「自分を数えるかどうか」で 1 つずれる混乱を避けられる。

## 11. POST `/api/cards/sort` — 全リストの優先度順並べ替え

ボード画面（SC-01）のツールバーにある「優先度順に並べ替え」で、3 つのリストすべてのカードを優先度順に並べ直す（[機能要件書](functional-requirements.md) FR-10、[データ要件書](data-requirements.md) 5. の D1）。

### 要求

パラメータも body も無い。

```
POST /api/cards/sort
```

### 処理

1. `lists` テーブルの全リストについて、順に次を行う。
   1. そのリストのカードを `displayOrder` の昇順で取り出す。
   2. [機能要件書](functional-requirements.md) 3.1 の規則で並べ直す：優先度が 高 → 中 → 低 の順、同じ優先度のカードどうしは今の順序を保つ（安定ソート）。FR-10 には「操作したカード」が無いので、末尾に置くカードも無い。
   3. `displayOrder` を 0 からの通し番号として書き込む。位置が変わったカードだけ `updatedAt` を現在時刻にする。
2. 3 リスト分を 1 つのトランザクションで行い、途中で失敗したらすべて取り消す（[データ設計書](data-design.md) 6.、決定事項 No.11）。

既に並んでいるリストは何も変わらない。何回呼んでも結果は同じ（冪等）。

### 応答

| ステータス | 本文 |
| --- | --- |
| 204 | なし |
| 500 | DB に接続できないなど。フロントエンドは「保存されていない」旨を通知する（FR-09） |

```
HTTP/1.1 204 No Content
```

### 並べ替え後に画面へ反映する方法

応答に本文が無いため、フロントエンドは成功後に `GET /api/cards`（6.）で全件を取り直して置き換える。3 リストすべての `displayOrder` が変わりうるので、リスト単位ではなく全件を取り直す（フロントエンド設計書 5.6）。

### なぜ `POST` で `/sort` なのか

「並べ替える」は取得・作成・更新・削除のどれにも当てはまらない **操作** であり、`PUT /api/cards/{id}` のように対象のリソースを 1 つ指すこともできない。このような操作は、コレクションのパスの下に動詞を置いた `POST /api/cards/sort` の形で表すのが一般的である。`PUT /api/cards` に全件の並びを送る形にすると、並べ替えの規則をフロントエンドが持つことになり、「規則はサーバーに置く」という方針（8.・9. の並べ替えと同じ）に反する。

### なぜ本文を返さず `204` にするのか

並べ替え後の全件を返すこともできるが、それは `GET /api/cards` と同じ形の応答を 2 つの API が返すことになる。登録・編集・移動（決定事項 No.9・16）と同じく「書き込んだらフロントエンドが取り直す」にそろえ、全件の応答は `GET /api/cards` の 1 か所にまとめる。返すものが無いので、`200` に空の本文ではなく、それを表す `204` を使う。

## 12. DELETE `/api/cards/{id}` — カードの削除

カード詳細（SC-02）の下部にある「カードを削除」から、不要になったカードを削除する（[機能要件書](functional-requirements.md) FR-03、[データ要件書](data-requirements.md) 5. の D2「削除」）。操作の手数を優先し、削除前の確認は求めない（[要件定義書](requirements.md) 決定事項 No.4）。

### 要求

| 種別 | 名前 | 型 | 必須 | 内容 |
| --- | --- | --- | --- | --- |
| パス | `id` | number | 必須 | 削除するカードの識別子 |

body は無い。

```
DELETE /api/cards/3
```

### 処理

1. `id` のカードを取得する（無ければ 404）。
2. そのカードの行を **物理削除** する（[データ設計書](data-design.md) 2. 方針 3。削除済みフラグは持たない）。
3. そのカードが属していたリストに残ったカードを `displayOrder` の昇順で取り出し、`displayOrder` を 0 からの通し番号として書き直す（[データ設計書](data-design.md) 6.「振り直しを行う操作」）。位置が変わったカード（削除したカードより後ろにあったもの）は `updatedAt` を現在時刻にする。
4. **優先度順の並べ替えは行わない**。削除で空いた分を詰めるだけで、残ったカードの相対的な順序は変えない。
5. 2〜3 は 1 つのトランザクションで行い、途中で失敗したらすべて取り消す。

### 応答

| ステータス | 本文 |
| --- | --- |
| 204 | なし |
| 400 | `id` が数値でない（例：`/api/cards/abc`）。2.1 の形式 |
| 404 | 指定した `id` のカードが存在しない。2.1 の形式 |
| 500 | DB に接続できないなど。フロントエンドは「削除されていない」旨を通知する（FR-09） |

```
HTTP/1.1 204 No Content
```

### 削除後に画面へ反映する方法

応答に本文が無いため、削除したカードがどのリストに属していたかは応答からは分からない。フロントエンドは **削除を要求する前に手元の一覧からそのカードの `listId` を控えておき**、成功後に `GET /api/cards?listId=<そのリスト>`（6.）でそのリストを取り直して置き換える。処理 3 のとおり残ったカードの `displayOrder` も変わるので、手元の一覧から 1 件を取り除くだけでは済まない（フロントエンド設計書 5.7）。

### なぜ本文を返さず `204` にするのか

削除したカードの内容を返すこともできるが、消えたリソースを受け取っても使い道が無い。全リストの並べ替え（決定事項 No.18）と同じく「返すものが無いときは `204`」にそろえる。

### なぜ 2 回目の削除が `404` になるのか

同じ `id` に 2 回 `DELETE` を送ると、2 回目は「カードが無い」ので 404 になる。「既に無いのだから成功（204）でよい」という考え方もあるが、本書では取得・編集・移動と同じく「パスで指定した `id` のカードが無ければ 404」に統一する。フロントエンドは手元の一覧にあるカードしか削除しないため、通常この状況は起きない。

### 確認や取り消しの仕組みを API に持たない理由

削除前の確認は画面側の話であり、API には関係しない。取り消し（アンドゥ）は本バージョンでは提供しない（[要件定義書](requirements.md) 8. 制約事項）ため、削除済みフラグを持って後から戻せるようにする「論理削除」も採らず、行を実際に消す（[データ設計書](data-design.md) 2. 方針 3）。
